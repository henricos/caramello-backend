# Architecture

## Overview

Caramello is a personal and family platform that centralizes the administrative side of family life — schedule, finances, shopping lists, health and entertainment — for a closed group of 1 to 5 people. The repository is a monorepo with two runnable modules and a relational database:

- **`apps/web`** — Next.js frontend. Drives the OAuth2/OIDC login (Keycloak in production, local mock in dev), keeps tokens only in the encrypted cookie and forwards the `access_token` server-side to the api. It is just one of the api's consumers, not the only one.
- **`apps/api`** — hybrid REST + MCP FastAPI backend, designed for multiple consumers (the web, other applications, AI agents). Validates the access token independently (JWKS/RS256, its own audience), authorizes via an e-mail allowlist and persists to PostgreSQL (automatic Alembic migrations at container boot).
- **PostgreSQL** — external in production; in dev, embedded (no installation required).

## Modules

- **`apps/api`** — owns the data model and all business rules. Its entities and business endpoints are declared in a YAML DSL and generated from it; see `apps/api/docs/architecture.md` and `apps/api/docs/dsl-rules.md`.
- **`apps/web`** — the single mobile-first interface for the family group, growing feature by feature as new domains are added to the menu.

## Data flow

1. Without a session, the web redirects the user to the OIDC provider; on the callback, it calls the api's `POST /auth/verify`, which validates the token, checks the allowlist and upserts the user in the database.
2. Once authenticated, the web consumes the api via Server Actions (`Authorization: Bearer <access_token>`); the api revalidates the token on every request.
3. Other consumers (applications, MCP agents on `/mcp`) present access tokens from the same realm, issued to their own clients with the api's audience, and go through the same authorization.
4. Every business read and write is additionally scoped to the caller's family membership — authentication establishes *who*, family membership establishes *what data*.

## Relevant decisions

Non-obvious cross-cutting decisions (those affecting more than one module or the deploy as a whole) are recorded here. Decisions local to a module live in the equivalent section of that module's own `architecture.md`.

**Configuration comes from the process environment; dev defaults are versioned, secrets are not.** No module reads a dotenv file on its own initiative and the repository ships no `.env.example`. Production receives variables directly from the orchestrator. Development uses one committed `.env.development` per module, holding only two kinds of value: throwaway local values (the embedded Postgres DSN, the mock OIDC issuer) that are meaningless outside the developer's machine, and `${VAR}` indirection to variables the developer already exports elsewhere for real external-service credentials. The raw secret never enters the committed file. This is deliberately not the more common `.env.example` + copy-to-`.env` pattern: that pattern produces a file nobody can validate, drifts silently from the code, and tempts a real secret into an ignored-but-local file. The api's `Settings` therefore sets no `env_file` and fails loudly on a missing required variable, with the shell responsible for loading (`set -a && source .env.development && set +a`) — which is also why `${VAR:-fallback}` works there. The web's file *is* auto-loaded by Next.js, whose loader is not a shell, so only plain `${VAR}` is valid there and defaults belong in its typed env validator. Full rules in `AGENTS.md`.

**Authentication model: the api as a standard OAuth2 resource server, with its own audience.** The api is designed for multiple consumers (the web is just the first; other applications and AI agents will come), so it follows the conventional design: each application has its **own client** in the single, fixed realm (e.g. `caramello-web`), the api has its **own audience** (`caramello-api`, added to the access tokens' `aud` via an audience mapper in the provider) and validates the **`access_token`** of any consumer through the same path (JWKS/RS256, `iss`, `exp`, `aud`). There is no re-authentication between layers: the web forwards the access token it already received at login. The provider (Keycloak) does **authentication only** — no permission, role or group is managed there. Authorization has two distinct layers in the application: the **e-mail allowlist** decides whether an identity may use the system at all, and **family membership** decides which data that identity may reach. Because of that, **every consumer has a human behind it**: even when another application or agent calls the api, the token comes from a user login and carries that user's e-mail. Service accounts (`client_credentials`, tokens without a user) are deliberately **out of scope**; if they ever exist, they will require a third authorization axis on the application side — never a permission in the provider.

**Public identifiers are UUIDs; integer ids never leave the api.** Every entity carries both an internal `id` (integer primary key, used for joins and foreign keys) and a public `uuid`. URLs, request bodies and responses use the `uuid` exclusively. The DSL's `expose_as_uuid` flag enforces this at generation time by substituting an integer foreign-key field with its UUID equivalent in the public schemas while the table keeps the integer column. The reason is twofold: sequential integers leak volume and enable enumeration, and the internal key stays free to change without breaking a published contract.

**No PostgreSQL schemas; isolation by table naming within a single database.** Each application group in the wider personal-app portfolio gets its own database, and inside it everything lives in `public`. Splitting into PostgreSQL schemas was evaluated and rejected as complexity without benefit at this scale. Related: each group's `users` table is its own island — a shared cross-group identity table was considered and discarded.

**The frontend is a server-rendered web application; native packaging is out of scope.** Earlier planning (`apps/api/docs/apps-platform.md`) called for React plus Capacitor packaged as a native mobile app. That decision is **reversed here**. The authentication model above depends on a server runtime that holds the tokens and never exposes them to the browser; Capacitor requires a static bundle and would force token custody onto device storage, weakening the single most important security property of the system. A server-rendered Next.js application, installable to the home screen as a PWA, covers the mobile-first requirement for a 1-to-5-user family group without that trade-off. If native presence ever becomes a real requirement, the path is a thin shell pointing at the published URL, not relocating token custody.

**Persistence uses SQLAlchemy 2 with separate Pydantic schemas, not SQLModel.** The module started on SQLModel, which unifies table and schema into one class. It was migrated because the unification is precisely what the project does not want: the public schema must diverge from the table (integer foreign keys must not leak — see the UUID decision above), so the "one class" benefit never materialized and the project had already grown a parallel hand-written schema layer to compensate. SQLModel also imposed two recurring hazards: a `session.exec()` / `session.execute()` split that silently produces row-wrapping type errors when mixed, and a rule that generated model files must never carry `from __future__ import annotations`, because deferred annotations break its relationship resolution. Plain SQLAlchemy 2 with typed `Mapped[]` columns removes both. The DSL that generates the models is unaffected in its inputs; only its emit templates changed.

**Money is `Decimal` end to end, `NUMERIC(15,2)` in the database.** No floating point appears anywhere in a monetary path, including parsers reading imported statements, which convert via `Decimal(str(value))`. A generator test asserts the absence of `float` in the finance models.

**"Competência" is an accounting dimension distinct from the movement date.** A financial entry records the period it belongs to (`competencia_year`, `competencia_month`) separately from the date the money moved. Reports aggregate by competência, never by movement date. This is why the pt-BR term survives in the schema: "accounting period" would be a lossy rename.

**Single access pattern: public URLs via Cloudflare Tunnel.** Each service publishes its port on the host and the tunnel's ingress rules point at `<SERVER_IP>:<port>` — addressing between applications is always the server's IP and a published port, never a container name or Docker's internal DNS; the external container network exists only to segregate the stack from the home network. Every consumer of the api, **including the web**, uses the same public URL (`API_URL`) — a single access pattern instead of a special internal path for the web. Pointing `API_URL` at `http://<SERVER_IP>:8000` is an optional latency optimization, to be adopted only if the round-trip cost through the tunnel actually matters (measured, not theoretical).

**No CI for now.** There is no test/lint workflow on push or PR; verification runs locally, driven by the AI (`docs/testing.md`), and the release gate is the manual checklist in each module's `docs/release.md`. CI will only be adopted once the homelab execution questions are resolved (a future discussion deliberately recorded here, so nobody "fixes" the absence before then).

**The repository ends at the release; publishing is the operator's job.** Each module's final deliverable is the image published to GHCR by the release workflow; there is no deploy documentation or automation in this repository. Where and how the images run is a personal procedure of the publisher's environment, kept outside the project.

**Variable docs live in each module's release guide; the compose example only encodes the stack.** The semantics of every runtime variable are documented once, in the "How to run the image" section of the owning module's `docs/release.md` (Docker Hub style: one image, one page). The root `compose.example.yaml` is not documentation: it is the machine-consumed artifact of the publishing handoff — the stack topology (service dependencies, healthchecks, the shared `/data` mounts, published ports) plus the `publish:*` interview markers that external publishing tools read to generate the real compose. Do not narrate variable meanings in compose comments; point to the release guides instead.

**Paired versions: all modules always release together.** The runnable modules share a single version number, bumped in lockstep: every release bumps `apps/api/pyproject.toml` and `apps/web/package.json` to the same `X.Y.Z` — even when only one of them changed — and the single `vX.Y.Z` GitHub release publishes BOTH images. The release workflow runs its guards once, asserts BOTH manifests against the tag and only then builds and publishes both images. The cost (occasionally rebuilding an image with no changes) buys a single tag namespace with no per-module prefixes, one canonical release flow, and a pair of images that are always known-compatible with each other. Never release one module alone or let the manifests drift apart.

**Automatic migrations at boot ⇒ api with a single replica.** The container entrypoint runs `alembic upgrade head` before starting the process, so publishing is just swapping the image tag, with no manual migration step. The accepted cost is running the api with a single replica (two replicas starting together would race for the migration). For this project's profile (single operator, small scale), trivial deploys are worth more than horizontal scale; if replicas ever become necessary, the path is moving the migration to a job separate from the deploy, not removing the automation.

**PUID/PGID adjustable at runtime, with privilege dropped via `gosu`.** Both modules follow the LinuxServer.io pattern (https://docs.linuxserver.io/misc/non-root/): the container starts as root, `entrypoint.sh` adjusts the image's `app` user to the `PUID`/`PGID` declared via environment (`usermod -o`/`groupmod -o`) and only then drops privilege via `exec gosu app` — the actual process never serves traffic as root. A `PUID`/`PGID` of `0` (root) is explicitly rejected by the entrypoint, before touching any user or file. The goal is to match the ownership of `/data` on the host with an arbitrary non-root user, without requiring an image rebuild per operator. Each Dockerfile also pins the same base image across all build stages: builder and runtime share the same libc (glibc), so a native dependency compiled in the builder never breaks only in production.

## Data folder

Both modules mount the shared `/data` folder (api with write access, web read-only). In dev it is a symlink or the `DATA_DIR` from the environment; in production, a host bind mount defined in the compose file.
