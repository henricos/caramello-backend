    Criar `Dockerfile` na raiz, multi-stage, conforme 05-PATTERNS.md §Dockerfile:
    ```dockerfile
    ARG APP_VERSION=0.0.0

    # Stage 1: builder
    FROM python:3.12-slim AS builder
    WORKDIR /app
    RUN pip install uv
    COPY pyproject.toml uv.lock ./
    COPY src/ ./src/
    COPY README.md ./
    RUN uv venv /app/.venv \
        && uv pip install --python /app/.venv/bin/python --no-cache .

    # Stage 2: runtime
    FROM python:3.12-slim AS runtime
    ARG APP_VERSION
    ENV APP_VERSION=${APP_VERSION}
    WORKDIR /app
    RUN addgroup --system app && adduser --system --group app
    COPY --from=builder /app/.venv /app/.venv
    COPY --from=builder /app/src ./src
    ENV PATH="/app/.venv/bin:$PATH"
    USER app
    EXPOSE 8000
    CMD ["uvicorn", "caramello.main:app", "--host", "0.0.0.0", "--port", "8000"]
    ```
    Pontos obrigatórios:
    - APENAS `APP_VERSION` é ARG. NUNCA `ARG DB_PASSWORD` ou `ARG KEYCLOAK_*` — credenciais ficariam visíveis em `docker history` (RESEARCH.md Pitfall 5 — T-05-10). Credenciais entram só como env vars em runtime via compose.
    - `USER app` (non-root) antes do CMD.
    - Runtime layer copia só o virtualenv e src — sem ferramentas de build.
    - `README.md` é copiado porque pyproject.toml referencia `readme = "README.md"` (a instalação falha sem ele).
    - Se `uv pip install --no-cache .` falhar no container, fallback documentado em 05-PATTERNS.md: `uv sync --no-dev`. Preferir a forma com `.` (instala o pacote a partir do pyproject).

| operador env → container runtime | Secrets injetados em runtime, não em build |

| T-05-12 | Elevation of Privilege | container user | mitigate | `USER app` (non-root) no runtime stage — processo uvicorn não roda como root |
