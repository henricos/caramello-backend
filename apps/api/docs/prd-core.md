# PRD Core – Authentication, Users and Families

## 1. Purpose of the Document

This document describes Caramello's core functional requirements related to user authentication, family management, roles, permissions and basic integrations. It serves as the functional reference for implementation, testing and evolution of the product, complementing the Project Vision.

This PRD does not address technical decisions, architecture, data modeling or framework choices.

---

## 2. Scope of the Core PRD (MVP)

### 2.1 Included Functionality

* User authentication
* Creation and management of families
* Owner and member roles
* Invites to join families
* Approval of requests
* Selection and switching of the active family
* Conceptual linking of integrations per user

### 2.2 Out of Scope

* Calendar functionality
* Lists, health, entertainment
* Specific integrations with external services
* Advanced permission settings

---

## 3. Fundamental Concepts

### User

Person authenticated in the system, identified uniquely and persistently.

### Family

Caramello's central organizational unit, where shared data is grouped.

### Family Owner

User responsible for creating the family, with exclusive administrative powers.

### Family Member

User participating in the family, with access to functionality according to the product's rules.

### Active Family

Family currently selected by the user for interaction in the system.

### Invite

Code or link generated by the owner to allow other users to request to join the family.

### Join Request

Request generated when a user uses an invite to join a family, subject to approval.

### Service Integration

Link between a user and an external service, granting access to specific functionality.

---

## 4. Roles, Permissions and Responsibilities

### Owner

* Create the family
* Generate and revoke invites
* Approve or reject join requests
* View and remove members

### Member

* Access the family's functionality
* View other members
* Request to leave the family

### Restrictions

* There is only one owner per family
* The owner cannot remove themselves

---

## 5. Authentication Flow

### 5.1 Initial Login

* The user logs in through an identity provider
* On first access, a new user is created

### 5.2 Active Session

* An authenticated user can access functionality according to permissions

### 5.3 Logout

* The user can end their session at any time

### 5.4 Re-authentication

* Expired sessions require a new login

---

## 6. Family Management

### 6.1 Family Creation

* An authenticated user can create a new family
* On creation, they automatically become the owner

### 6.2 Selection of the Active Family

* Users with only one family have it selected automatically
* Users with multiple families must choose an active family

### 6.3 Switching the Active Family

* The user can switch the active family at any time

---

## 7. Invites and Joining Families

### 7.1 Invite Generation

* Only the owner can generate invites
* Invites are reusable
* Invites can be revoked

### 7.2 Join Request

* An authenticated user uses an invite to request to join
* The request stays in a pending state

### 7.3 Approval or Rejection

* The owner approves or rejects requests
* Approval grants immediate access
* Rejection closes the request

---

## 8. Family Member Management

* The owner can view all members
* The owner can remove members
* A member can request to leave voluntarily

---

## 9. Service Integrations (Overview)

* Integrations are linked to users
* Each integration has its own state (active, revoked, error)
* Functionality depends on the integration being active

---

## 10. General Privacy and Access Rules

* Data is always isolated by family
* Individual data is not shared automatically
* Access to sensitive data must be explicit

---

## 11. States, Errors and Exceptional Situations

* Access without an active family is not allowed
* An invalid invite produces an informative error
* Duplicate requests are not allowed
* Integration failures must be communicated

---

## 12. User Experience (Functional View)

### Onboarding

* Login
* Creation of or joining a family

### User Without a Family

* Can create a family or enter an invite

### User With a Pending Request

* Access blocked until the owner decides

### User With Multiple Families

* Must choose an active family

---

## 13. Out of Scope and Deferred Decisions

* Additional roles
* Delegation of permissions
* Automations

---

## 14. General Acceptance Criteria (Core)

* Consistent user identity
* Total isolation between families
* Clarity in access states
* Predictable and safe behavior

---

## 15. Final Considerations

This Core PRD establishes Caramello's functional baseline. Additional functionality must be described in specific PRDs, keeping this document stable and focused on the system's core.
